# 9 Pro / 10 Pro 共用兼容试验与反馈指南

本轮已发布：手机 **0.4.1 / code 26**、手环 **0.5.1 / code 25**；[v0.5.1-preview.1（Pre-release）](https://github.com/worlt/wrist-navigation/releases/tag/v0.5.1-preview.1)，不是Latest。8组CI与七附件匿名下载核对通过；此前v0.5.0-preview.1和正式Latest附件不变。手环界面不增加排查模式，诊断全部在手机操作。

> 2026-11-23 已收到 9 Pro 用户截图：高德通知解析成功、手机 SDK 发送成功但没有确认、手环“发送失败 (202)”。代码中首参数错误码遗漏和异步格式降级竞态已由回归测试复现；截图不能区分具体回调形态，也不能证明这就是全部实机根因。没有可用 9 Pro 实机或完整固件日志，**不代表双机兼容已通过**。此前“9 Pro 最高可用 040”的反馈仍只是用户观察范围。

## 先安装什么

- 手机安装 NAV-PHONE-041.apk；手环先尝试 **NAV-BAND-051-NOFONT.rpk**。它只是去掉大字体资源，核心代码与完整版相同，不是 9 Pro 专用版。
- 需要字体时再试 NAV-BAND-051.rpk。两份 RPK 只能二选一，不能并存。大 TTF 的加载、固件内存与功耗仍需实测。
- 包名和原配对签名不变，APK/RPK 仍是原签名 debug 构建。安装前核对 SHA256SUMS.txt，不要安装 unsigned 包。
- 首次测试请手动打开手环应用一次：040 风格的互联初始化现在等待首屏 onReady，之后仍由 App 会话继续接收。没有打开页面前不承诺后台提醒。
- 当前正式 Latest 保持 v0.4.8，本试验不替换正式版，也不改旧附件。

## 2026-11-23 针对 202 反馈的修复

1. 回调第二参数、首参数的 code 字段、同步异常的 code 字段统一处理；202 触发一次单层嵌套重试，覆盖 ready、ACK、版本、诊断及显示报告。
2. 每次发送捕获自己的封包格式；异步返回的 202 不会被另一条消息修改的全局偏好吞掉。只有成功发送才选择嵌套偏好，已完成/销毁的回调不再生效。
3. 两种格式都被 202 拒绝时记录回传参数失败，不把它当作物理断连，不让 ACK 的参数错误遮掉已收到的导航。onclose/1006 等真实断连仍按原规则处理。
4. 手机重连只取消当前诊断读取；进程内收发计数、拒收分类和历史报告保留。新连接显示“当前连接尚未读取”，不会把注册监听写成已收到手环数据。

手机 040 的 v1 接收协议也可配合手环 051，通信修复在手环端；推荐一起安装手机 041 以获得保留证据的诊断。回传仍完全失败时手机无法取得手环内部计数，请继续反馈完整失败报告和手环照片。

## 保留的上一轮兼容措施

1. 原生互联和提醒存储的首次读取延后到首屏就绪，不在 App.onCreate 提前初始化，兼容老固件启动阶段；页面关闭后仍保留 App 级会话。
2. 连接状态支持数字 1 与字符串 "1"；getReadyState 缺失时保留已注册的消息回调，不假定连接成功。实际 onopen / 合法导航包可确认连接。
3. 版本、内部诊断回复遇 202 参数错误时，也进行一次单层嵌套发送降级；手机严格解一层 data 字符串包装，保留原设备、协议、ACK 的 session/sequence 检查。
4. 振动、退出、常亮等可选 API 异常不阻断基础导航/ACK；记录有界的阶段、错误类型与数值代码。
5. 手机同步诊断新增“读取手环诊断”和“复制兼容诊断（无路线）”。只在用户点击读取时查询，不上传、不引入账号或服务器。

未证实的安装声明问题不靠盲删 system.app/system.vibrator 处理；两机共享分辨率也不能证明固件接口相同。

## 用户最短反馈流程（能打开应用）

1. 记录手环型号、固件版本、手机系统、手机/手环应用版本和 RPK 文件名。不要只写 Release 标签，标签号不是包内版本。
2. 连接小米运动健康并完成互联授权；手动打开手环“腕上导航”，在安全的静止位置开始高德导航。
3. 手机“腕上导航”首页展开 **同步诊断**，点 **读取手环诊断**，等最多 5 秒。
4. 点 **复制兼容诊断（无路线）**，把文本发给维护者。成功显示“本次读取”；再次读取超时或失败时，旧记录明确标为“历史读取”，不能冒充本次结果。
5. 另写“预期是什么、实际是什么、何时出现、复现步骤”。例如前台显示正常但切后台停止，注明是手机后台、手环回表盘还是熄屏。
6. 若是方向/距离解析问题，再单独使用原“复制当前诊断”；**这份旧报告包含通知/路线原文，分享前必须隐藏私人地点**。无路线报告不包含这些文本。

读取手环内部诊断要求安装本轮双端包并已经运行过手环页面。旧手环版本会忽略新查询，这是可能的超时原因之一，不是明确的崩溃证据。

## 按失败阶段定位（这次没修好也照此收集）

### A. 安装失败：进不了应用

- 先用无字体版、确认文件下载完整、SHA-256 与清单一致。
- 拍下安装器的完整错误，记录安装工具/版本、手环固件、所选文件、原来是否已装 040，以及是否覆盖安装。**手机应用不能读取手环安装器或固件崩溃日志**。
- 若安装工具提供日志导出，只导出本应用 io.github.mi9pro.navigation 对应时间段；去掉账号、设备标识和私钥。没有日志功能就提供照片与步骤，不必猜错误名称。
- 不要反复盲目卸载或降级。卸载会清掉手环设置并可能需要重新授权。回退 040 是否需要卸载，由安装器的真实提示决定。

### B. 点开即退出 / 黑屏：进不了诊断

- 记录从点击到退出的时长，短视频/照片，以及无字体版是否也如此。
- 手机点“读取手环诊断”，反馈失败/超时报告；它可以提供手机收发计数，但**不能证明手环初始化哪一行崩溃**。
- 若安装/开发工具能捕获应用日志，在重现一次前开始捕获，限定该包名和时间段；提供固件/工具版本与日志，先脱敏。不要上传其他应用的通知或整机日志。

### C. 能打开，但收不到导航

- 首先手动开手环应用再查诊断；核对手机通知监听是否已连接、手机系统是否允许腕上导航和小米运动健康后台运行。
- 手机接收计数为本次手机进程累计，含重连前；匹配设备表示接收时匹配目标设备。旧手机040会在重连时清零，所以旧报告的收到=0不能证明从未收到任何消息。手机 SDK 发送成功也不是手环 ACK。收到=0，优先核查互联/监听/手环是否运行；收到>0但匹配设备=0，核查配对/授权设备；已解包=0或拒收增长，反馈具体拒收分类。
- 手环内部计数：rx=0，手机→手环还没观察到消息；rejected 增长说明收到但协议/顺序未接受；accepted 增长且手机 ACK 不增长，调查回程/封包；accepted/ACK 都增长但显示仍不变，调查页面可见性和固件渲染。**这些是分流证据，不是单凭一个数断定根因**。
- ready-missing：固件没有可调用的状态检查方法，不等于互联完全不可用；link-init / ready-fail / send-fail 配合错误类型和 #代码反馈。

### D. 导航能显示，但振动、退出或常亮异常

- 反馈手机偏好开关、手环页面可见/隐藏、锁屏状态及复现步骤，不新增手环排查模式。
- 内部阶段 vibrate / terminate / screen 对应相关调用；#0 只表示未提供数值错误码，**不证明实际振动或物理屏幕成功**。
- 先保留正常显示的结果，再读一次诊断，不用把接口问题和通知解析混为一谈。

## 隐私与能力边界

- 手环内部记录仅内存保存最近16条，计数饱和到999999；没有路线、原始消息、错误 message/stack、设备ID、令牌或持久日志。进程重启后记录丢失。
- 手机只有用户点击才发 diagnostics-query；手环只回复合法、限频查询。手机只接受当前授权设备、当前请求、5秒内、白名单版本/计数/事件；不会自动重试或自动上传。
- 手机本机型号、系统与版本会写进用户主动复制的无路线报告。所有诊断留在设备/剪贴板，分享由用户决定。
- 当前手机不能拉取手环固件安装/启动崩溃栈。安装和启动失败仍依赖用户工具日志或照片。
- 本实验未合入原 main 的昨天手机037/038/039和手环049未提交候选；只复用其中已测试的单层 PeerPacket 解析器，重新写本分支的安全回归。
